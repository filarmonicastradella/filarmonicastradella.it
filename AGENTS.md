You are able to use the Svelte MCP server, where you have access to comprehensive Svelte 5 and SvelteKit documentation. Here's how to use the available tools effectively:

## Available Svelte MCP Tools:

### 1. list-sections

Use this FIRST to discover all available documentation sections. Returns a structured list with titles, use_cases, and paths.
When asked about Svelte or SvelteKit topics, ALWAYS use this tool at the start of the chat to find relevant sections.

### 2. get-documentation

Retrieves full documentation content for specific sections. Accepts single or multiple sections.
After calling the list-sections tool, you MUST analyze the returned documentation sections (especially the use_cases field) and then use the get-documentation tool to fetch ALL documentation sections that are relevant for the user's task.

### 3. svelte-autofixer

Analyzes Svelte code and returns issues and suggestions.
You MUST use this tool whenever writing Svelte code before sending it to the user. Keep calling it until no issues or suggestions are returned.

### 4. playground-link

Generates a Svelte Playground link with the provided code.
After completing the code, ask the user if they want a playground link. Only call this tool after user confirmation and NEVER if code was written to files in their project.

### HTML e progressive enhancement
- Il sito deve funzionare come HTML semantico anche senza CSS e senza JS: il JS aggiunge solo miglioramenti.
- Sezioni con titolo: `<section>` con il suo `<h2>` come primo figlio (il componente `Section` non c'è più). Un solo `h1` per pagina; gerarchia dei titoli senza salti.
- Elenchi di elementi equivalenti in `<ul><li>`; date in `<time datetime>`; coppie etichetta/valore in `<dl>`; niente `<header>`/`<footer>`/`<address>` dentro i link né `div` usati solo per il layout.
- Pagine non ancora pronte: `<h1>`, una riga di presentazione e "Pagina in costruzione: …"; bozze legali con il commento `<!-- BOZZA … -->` in testa da far verificare prima della pubblicazione.
- Spiegazioni aggiuntive di una pagina (aiuto, piccole FAQ): sempre l'ultima sezione della pagina, dopo i moduli e prima del rimando in fondo (dal 1/11/2026); una sezione con `<h2>` e un `<details>`/`<summary>` per domanda, senza JS; stili generali in `content.css`. *(Dal 29/10/2026.)* Niente domande frequenti nelle pagine del menu che sono solo indici di schede (Associazione, Le nostre formazioni, Sostienici: dal 3/11/2026); Le ha la pagina del modulo per scriverci (`/contatti/scrivi`), e cambiano con il motivo; Contatti, che dal 8/11/2026 ha solo i recapiti e il pulsante verso il modulo, no. Ogni domanda sta in una pagina sola, quella dove la cerca chi legge (Iscrizione: le pratiche, anche come si entra in una formazione e se serve uno strumento proprio; ogni formazione: chi dirige, chi sceglie i brani e come proporre una nuova formazione, condivise in `faq.ts`; Contatti e la pagina degli ingaggi: gli ingaggi; pagina di un evento: ingresso, prenotazione, pioggia), senza riempire le pagine di domande e senza ripetere in una sottopagina quelle della pagina superiore (le formazioni non ripetono Le nostre formazioni, che non ripete Associazione; l'iscrizione non ripete Sostienici); le poche che servono davvero in più pagine hanno la risposta in un punto solo, `src/lib/faq.ts`, e si inseriscono con `<FaqItem item={faq.…} />`.
- Incorporazioni di terze parti (mappe): caricate solo su richiesta con un pulsante (`MapEmbed`), con il link diretto sempre visibile.
- Elenchi datati (eventi) con il componente `TimelineSections`: sezioni per anno (solo se più di uno) e mese, con indice di navigazione annidato; l'ordine è quello degli elementi passati (eventi dal più vicino).
- Elenchi in ordine cronologico in `<ol>`; eventi con microdati schema.org (`itemscope itemtype="https://schema.org/Event"`, `itemprop`), indici di sezione come `<nav>` con collegamenti interni.
- Struttura di ogni pagina, sempre la stessa: intestazione (`<header>`: occhiello, `h1`, presentazione, eventuali note come la data di aggiornamento o il credito della foto), poi blocchi (sezioni con il loro `h2`, elenchi di schede, moduli, indici di sezione), poi in fondo, solo nelle pagine sotto il primo livello (non raggiungibili dal menu) e nei singoli elementi di una raccolta (un evento, un articolo, una formazione), il rimando alla pagina superiore (`<p class="rimando">`, per esempio «Calendario», «L'associazione»). Gli altri inviti verso altre pagine (per esempio agli ingaggi) non sono rimandi in fondo: sono una sezione con titolo e una frase con il link nel testo. Mai testo sciolto in `main`: un'introduzione va nell'intestazione, il resto in una sezione con titolo. Così gli stacchi verticali sono quelli di `layout.css` ovunque: 6rem tra i blocchi, 1,5rem tra i paragrafi. *(Dal 29/10/2026.)*
- Ogni pagina ha `<main id="contenuto">` (bersaglio del link "Salta al contenuto"), `<title>` e meta description.

### CSS

- Gli stili *generali*, usati in più di una pagina o componente, stanno nei file di `src/lib/styles/` (selettori di elementi, ruoli, ARIA e microdati, per esempio `main > header`, `li:has(> article)`, `[role="group"]`, `ol[tabindex="0"]`; niente classi né id, se non strettamente necessari e con nomi standard e comprensibili). Le particolarità di un singolo componente o pagina (per esempio la spaziatura interna della hero) stanno in un `<style>` dentro quel file stesso, non nei file generali — sempre con i token (`var(--...)`), mai valori diretti. *(Dal 3/10/2026: prima la regola era "niente `<style>` nei componenti", superata — si è rivelato più chiaro separare così il generale dallo specifico.)*
- Il design system (colori, tipografia, logo, elementi grafici, componenti, tono di voce) è in `docs/DESIGN.md` ed è la regola: il sito è HTML semantico da vestire secondo il design system, e quando una scelta precedente lo contraddice vince il design system. Va letto prima di toccare stili o testi. *(Dal 9/10/2026.)*
- File in `src/lib/styles/`, caricati in `+layout.svelte`: `typography.css` (Cormorant Garamond 500/600 solo per i titoli da 24px in su, Plus Jakarta Sans per il testo, scala `--fs-*`; maiuscolo spaziato solo per date, indici in cima alle pagine, occhiello della home e «Menu», dal 7/11/2026: categorie, testate, etichette e rimandi in tondo), `colors.css` (tavolozza `--color-*` e ruoli `--bg`, `--text`, `--text-brand`, `--accent`…: nelle regole si usano solo i ruoli; tema scuro automatico con il rosa velluto al posto del bordeaux; il piè di pagina è una superficie scura fissa), `layout.css` (spaziature `--space-1`…`--space-10`, contenitori, forma, movimento, corde, intestazione di pagina, piè di pagina). I nomi dei token sono quelli del design system, `content.css` (testo, elenchi, schede, tabelle, figure, finestre), `forms.css` (moduli e pulsanti). Nel codice usare i token (`var(--...)`), mai valori diretti.
- L'intestazione è `fixed`, sempre opaca, alta `--header-height`; lo spazio nel flusso lo riserva `main`. A sinistra il logotipo orizzontale (simbolo e il nome su due righe alla stessa larghezza: «A. Stradella» in Cormorant Garamond 600 sotto, più grande, con «Alessandro» in un `<abbr>`, e sopra «Filarmonica» nel maiuscoletto vero del Garamond (Cormorant SC 600 in `static/fonts/`), più piccolo, spaziato fino alla stessa larghezza; dal 7/11/2026). Il menu (`SiteMenu.svelte`) contiene le voci di `navItems` e un pulsante a contorno, "Sostienici" (`/sostienici`; fino al 29/10/2026 era "Unisciti a noi", verso l'iscrizione; pieno fino al 4/11/2026, ora il pulsante pieno è l'azione della pagina, vedi `docs/DESIGN.md` §10): da 64rem in linea nell'intestazione, sotto 64rem in un pannello a tutto schermo aperto dal pulsante del menu (tre corde distese, area di tocco 48px, che ruota di 90° allineandosi alle corde del pannello), con le voci in Jakarta e il pulsante in fondo. All'apertura il pannello sfuma e le voci salgono in sequenza; a menu aperto la pagina non scorre (`html:has(nav[data-open])`, CSS); `afterNavigate` lo chiude dopo la navigazione. *(Dal 9/10/2026.)*
- Rimandi («Calendario →»): `<p class="rimando"><a href="...">…</a></p>`, solo per paragrafi fatti di un unico link interno. In home ogni sezione finisce con il rimando alla pagina che riassume (dal 4/11/2026): non è un rimando alla pagina superiore, ma è il passo successivo della sezione, e ha lo stesso aspetto. La classe è necessaria: il CSS non distingue un paragrafo di solo link da un paragrafo di testo con un link dentro, e senza classe il testo normale finiva in maiuscoletto con la freccia. Il testo del rimando è il nome della pagina di arrivo, come nel menu (per le voci del menu vince il nome della voce: «Associazione», non «L'associazione»; dal 4/11/2026) e nel suo titolo (non «Come iscriversi» per «Domanda di iscrizione»); nel testo «consiglio direttivo» va minuscolo, e i gruppi della Filarmonica sono «formazioni», non «ensemble». *(Dal 29/10/2026; nomi uniformati il 1/11/2026.)*
- Disegni a un solo inchiostro su fondo trasparente (il fregio del sonetto, la lapide degli Stradella): PNG in nero con la trasparenza, dentro `<figure class="inchiostro">`, che li schiarisce nel tema scuro. La classe serve perché il CSS non distingue questi disegni dalle foto. *(Dal 30/10/2026.)*
- Le schede sono cliccabili per intero con un `<a>` vero che avvolge tutto il contenuto (titolo e testo), non solo il titolo: `<li><a href="..."><h3>Titolo</h3><p>Testo</p></a></li>`. Scelta consapevole rispetto al `::before` esteso: chi usa uno screen reader sente l'intero testo della scheda come nome del link, non solo il titolo, ma il markup resta più semplice. I selettori CSS che riconoscono una scheda richiedono sempre un titolo dentro il link (per esempio `li:has(> a > :is(h2, h3, h4))`), mai un `<a>` generico, per non intercettare i link semplici nelle liste (menu, footer, indici).
- SvelteKit avvolge l'app in un `div` senza aspetto: per questo i selettori di intestazione e piè di pagina sono `body > div > header` e `body > div > footer`.
- Icone: regole nella sezione Iconografia di `docs/DESIGN.md` (Heroicons in una sola variante, Simple Icons solo per i loghi dei social, monocromatici; solo funzionali, mai decorative né strumenti musicali; `currentColor`; 1em accanto al testo, 1,25rem in pulsanti e social, massimo 24px; sempre `aria-hidden` con una parola accanto; niente emoji). Si importano con `unplugin-icons` (`~icons/heroicons/...`, `~icons/simple-icons/...`), che le incorpora nella build come componenti: nessuna richiesta esterna, niente `@iconify/svelte` (scarica le icone a runtime). L'icona del menu sono tre corde disegnate in CSS (tre `span` con lo spessore e la distanza delle corde), non un'icona del set: aprendo il menu ruota di 90° e diventa la cima delle corde del pannello. Le frecce dei link esterni e dei rimandi restano maschere CSS (`--icon-external`, `--icon-next` in `content.css`) perché devono comparire da sole su ogni link, senza toccare l'HTML; i tracciati vengono dallo stesso set. Lucide e Phosphor sono stati provati e scartati (Lucide non ha uno stile pieno; Phosphor "fa schifo"). *(Dal 9/10/2026.)*
- Design: quello di `docs/DESIGN.md`. Carta, inchiostro e un solo colore di marca, il bordeaux; titoli in Cormorant, testo in Jakarta; angoli quasi vivi (`--radius: 2px`); schede con solo il filetto in alto (`--rule-width` in `--border`, bordeaux al passaggio del mouse), senza fondo né bordo; le corde (tre linee verticali, con i pallini dove finiscono dentro la pagina) nelle intestazioni di pagina (in copertine e hero sotto la foto, accanto al testo), nel menu (lunghe quanto le voci) e nel piè di pagina, sempre sul bordo destro del contenitore e mai sopra le foto (dal 20/10/2026), definite una volta sola in `layout.css`. *(Dal 9/10/2026: sostituisce "niente riquadri, `--radius: 0`"; le schede sono tornate al solo filetto dopo una breve prova con fondo e bordo.)*
- Movimento: regole nella sezione Movimento di `docs/DESIGN.md` (accompagna, non si esibisce; solo opacità, spostamenti fino a 1,5rem e colori; niente animazioni allo scorrimento, parallasse, caroselli automatici, autoplay, contatori; con `prefers-reduced-motion` niente spostamenti). Durate solo con i token di `layout.css`: `--duration` (180ms, colori e hover), `--duration-slow` (300ms, menu, riquadri, finestre, cambio di pagina), `--duration-entrance` (700ms, solo comparse della prima schermata), `--stagger` (80ms, scarto tra elementi in sequenza); andamento sempre `--ease`. Unica rotazione ammessa: il pulsante del menu che si gira sulle corde. Mai durate scritte a mano nei componenti. Cambio di pagina con le View Transitions (`onNavigate` in `+layout.svelte`, CSS in `layout.css`): l'intestazione ha un suo `view-transition-name` e resta ferma. *(Dal 9/10/2026.)*
- Il 29/9/2026 il sistema di stile è stato azzerato per ripartire dall'HTML semantico; il 10/10/2026 sono state eliminate le vecchie versioni archiviate (`.old-components/`, `.old-styles/`) e i componenti di confronto: il riferimento è solo `docs/DESIGN.md`.

- Codice pulito e non ridondante: nessuna regola CSS ripetuta in più punti (se serve in più contesti va scritta una volta sola con un selettore generale), nessun attributo o ruolo ARIA che ripete ciò che l'elemento già è (per esempio `role="list"` su un `ul`), nessun elemento o file superfluo.

### Svelte
- Svelte 5 idiomatico: rune (`$state`, `$state.raw` per dati solo riassegnati, `$derived`, `$props`), `{@attach}` per il comportamento sul DOM (in `$lib/attachments.ts` quando serve), `<svelte:window>`/`<svelte:document>` per gli eventi globali, `each` con chiave. Niente DOM imperativo, `setInterval` di polling o `$effect` per sincronizzare stato.
- Usare le skill `svelte-code-writer` e `svelte-core-bestpractices` e controllare con `svelte-check` e `html-validate`.

### Struttura dei file
- Componenti usati da una sola pagina accanto a quella pagina (`src/routes/`); componenti condivisi in `src/lib/components/`.
- Logica di accesso ai dati in `src/lib/` (`events.ts`, `gallery.ts`, `articles.ts`); contenuti Markdown in `src/lib/content/`.
- Sviluppo: una funzionalità nuova si scrive tutta in un unico file (pagina o componente) e si estrae in componenti o moduli solo quando il file diventa troppo lungo o complesso, non prima e non per semplice somiglianza tra due punti. Le estrazioni si fanno per passi, con un commit per passo.

### Contenuti
- Strumenti: la Filarmonica ne presta alcuni, non tutti (certi costano troppo); le parti e la sala prove le mette sempre. Mai scrivere che fornisce lo strumento a tutti. *(Dal 3/11/2026.)*
- «Banda» mai riferito alla Filarmonica o alle sue formazioni; si può usare per gli altri enti («le bande e le realtà musicali amiche della Lunigiana», «le bande di paese»). *(Dal 1/11/2026: precisa il divieto generale di `docs/DESIGN.md`.)*
- L'associazione non dà rilievo a una figura di direttore: i direttori sono più di uno e sono considerati alla pari degli altri musicisti. Niente pagine, titoli o sezioni dedicati a un direttore; eventuali nomi compaiono nelle schede delle formazioni insieme agli altri componenti.
- Ipertestualità: meglio pagine brevi e collegate tra loro (collegamenti nel testo, rimandi a pagine correlate) che pagine lunghe con tutto insieme. Quando una pagina cresce troppo si divide in pagine più piccole con un indice e con la navigazione tra una e l'altra.
- I segnaposto vanno scritti nella forma finale: link veri, dati nel formato definitivo, anche se per ora non puntano a niente o sono valori finti. Il segnaposto si segnala con un commento `SEGNAPOSTO` nell'HTML, non con un testo alternativo diverso dalla forma finale. I testi segnaposto si mostrano in modo visibile tra parentesi quadre (per esempio "[Descrizione da inserire]"), così non si scambiano per contenuti veri.
